## Dos bugs que ya has visto

Pides los pedidos a tu API y los ordenas por fecha:

```jsx
const res = await fetch("/api/orders");
const orders = await res.json();

orders.sort((a, b) => b.createdAt.getTime() - a.createdAt.getTime());
// TypeError: b.createdAt.getTime is not a function
```

En el backend `createdAt` era un `Date`. En el cliente es un string. Y en otro componente, el carrito "se guarda" pero al recargar aparece vacío:

```js
localStorage.setItem("cart", cart);
localStorage.getItem("cart"); // "[object Object]"
```

Los dos bugs tienen la misma raíz: no saber exactamente qué es un objeto, qué es un array y qué sobrevive cuando los conviertes en texto. Ya usas objetos y arrays a diario; aquí vamos directos a los bordes donde se rompen.

## Objetos: punto vs corchetes

Un objeto es una colección de pares clave/valor. Las claves son strings (o Symbols); todo lo demás se convierte en string.

```js
const user = { name: "Ana", "full-name": "Ana Ruiz", 1: "uno" };

user.name;          // "Ana"
user["full-name"];  // user.full-name se leería como user.full - name (una resta)
user[1];            // "uno": la clave real es el string "1"
```

La regla para elegir:

- **Punto** (`obj.clave`): el nombre es literal y es un identificador válido. Es lo normal.
- **Corchetes** (`obj[expr]`): se **evalúa** la expresión y su resultado (convertido a string) es la clave. Hace falta cuando la clave está en una variable, viene de fuera o no es un identificador válido (`"full-name"`, `"1"`, `"data-id"`).

El error clásico es usar punto con una variable: `obj.key` busca la propiedad que se llama literalmente `"key"`, no la que indica la variable `key`.

### Claves computadas y shorthand

En un literal, los corchetes también sirven para calcular la clave. Es lo que usas en el `handleChange` genérico de un formulario:

```jsx
function handleChange(e) {
  const { name, value } = e.target;
  setForm((prev) => ({ ...prev, [name]: value })); // clave computada
}
```

Y el **shorthand** ahorra repetir nombres en propiedades y métodos:

```js
const name = "Ana";
const age = 30;

const user = {
  name,               // equivale a name: name
  age,
  greet() {           // equivale a greet: function () { … }
    return "Hola, " + this.name;
  },
};
```

## Propiedades que no existen

Leer una propiedad que no existe **no es un error**: devuelve `undefined`. El error llega al ir un nivel más:

```js
const res = { data: {} };
res.data.user;        // undefined, sin error
res.data.user.name;   // TypeError: Cannot read properties of undefined
res.data.user?.name;  // undefined: optional chaining corta la cadena
```

Esto es lo que pasa en el primer render de un componente cuando los datos todavía no han llegado y haces `data.user.name`. El `TypeError` no está en la línea que "falla", sino en la suposición de que el nivel anterior existía.

Como leer da `undefined` tanto si la propiedad no existe como si existe con valor `undefined`, para distinguirlo tienes el operador `in`. Y para quitar una propiedad, `delete` (asignar `undefined` no la elimina):

```js
const settings = { theme: "dark" };
"theme" in settings;     // true
delete settings.theme;   // la propiedad deja de existir
"theme" in settings;     // false
```

<Pregunta id="objetos-inexistente-in-delete" />

<Callout type="nota">
`in` también encuentra propiedades heredadas: `"toString" in {}` es `true`. Para preguntar solo por las propias existe `Object.hasOwn`. La diferencia, junto con `Object.keys`/`entries` y el orden de las claves, se ve a fondo en el módulo de JavaScript profundo ("Objetos y colecciones"). Igual que por qué `{}` no es igual a `{}` y qué significa copiar un objeto: eso es "Valores y referencias".
</Callout>

### Objetos como diccionarios

Con corchetes, un objeto sirve de diccionario con claves dinámicas:

```js
const countByStatus = {};
for (const order of orders) {
  countByStatus[order.status] = (countByStatus[order.status] ?? 0) + 1;
}
// { paid: 12, pending: 3 }
```

Funciona bien con claves de tipo string controladas por ti. Si las claves no son strings o vienen del usuario (y una podría llamarse `"constructor"` o `"__proto__"`), un `Map` es mejor herramienta; también está en el módulo 3.

## Arrays: índices y length

Un array es un objeto especial cuyas claves son índices (`"0"`, `"1"`…) y que mantiene `length` sincronizado. Lo importante:

```js
const list = ["a", "b", "c"];
list[10];        // undefined, sin error (como cualquier propiedad inexistente)
list.at(-1);     // "c": at acepta índices negativos
list[-1];        // undefined: con corchetes, -1 es solo la clave "-1"
Array.isArray(list);  // true (typeof list es "object")
```

`length` no es solo de lectura. Asignarlo **trunca o amplía el array en sitio**:

```js
list.length = 1;   // list es ["a"]
list.length = 3;   // list es ["a", <2 huecos>]
```

Esos **huecos** (*holes*) no son `undefined`: son posiciones que no existen. Aparecen con `new Array(3)`, con `[1, , 3]` o al ampliar `length`, y cada método los trata a su manera (`forEach` y `map` se los saltan, `join` los convierte en cadenas vacías). No los crees a propósito: si necesitas un array de N elementos, usa `Array.from({ length: n }, (_, i) => i)` o `new Array(n).fill(0)`.

<Pregunta id="arrays-length-vaciar" />

`list.length = 0` como forma de "vaciar" es justo el problema: vacía el array que comparten todos los que tienen una referencia a él (por ejemplo, el estado de React o una prop). Si quieres "una lista vacía", asigna una nueva: `setItems([])`.

## Métodos que mutan y métodos que no

En React esta es la distinción que más importa: si mutas el array del estado y llamas a `setState` con el mismo array, React compara con `Object.is`, ve la misma referencia y puede no volver a renderizar.

| Mutan el array original | Devuelven un array nuevo |
|---|---|
| `push(x)`, `unshift(x)`: devuelven el nuevo `length` | `concat(x)`, `[...arr, x]` |
| `pop()`, `shift()`: devuelven el elemento quitado | `slice(inicio, fin)` |
| `splice(i, n, ...items)`: devuelve **los eliminados** | `toSpliced(i, n, ...items)` |
| `sort(fn)`: devuelve el mismo array | `toSorted(fn)` |
| `reverse()`: devuelve el mismo array | `toReversed()` |
| `arr[i] = x`, `fill(x)` | `with(i, x)` |

Fíjate en la columna de los que mutan: **lo que devuelven** también confunde. `push` no devuelve el array (devuelve un número), `splice` devuelve lo que quitó, y `sort`/`reverse` devuelven el mismo array, así que `const sorted = arr.sort()` parece una copia y no lo es. `toSorted`, `toReversed`, `toSpliced` y `with` (ES2023) existen precisamente para tener la versión que no muta de cada uno. Además, `with` lanza `RangeError` si el índice está fuera de rango, en vez de crear huecos.

## Buscar: includes vs indexOf

`indexOf` compara con `===`, y como `NaN === NaN` es `false`, nunca encuentra `NaN`. `includes` usa otro algoritmo (*SameValueZero*) que sí lo encuentra. Si solo quieres saber si algo está, `includes` es más claro; usa `indexOf` cuando necesites la posición (ojo: los dos comparan objetos por referencia, así que para buscar un objeto por su contenido usa `find`/`findIndex` con una condición).

## JSON: el formato de texto

JSON es un formato de **texto** con una sintaxis inspirada en los literales de JavaScript, pero mucho más pobre: strings (siempre con comillas dobles), números finitos, `true`/`false`, `null`, arrays y objetos con claves string. Nada más.

```js
const text = JSON.stringify({ id: 1, tags: ["a"] }); // '{"id":1,"tags":["a"]}'
const data = JSON.parse(text);                        // un objeto nuevo
```

Esto explica el segundo bug: `localStorage` solo guarda strings, y `setItem` convierte el valor con `String(value)`. Un objeto convertido a string es `"[object Object]"`. Hay que serializar tú:

```js
localStorage.setItem("cart", JSON.stringify(cart));
const cart = JSON.parse(localStorage.getItem("cart") ?? "null");
```

### Qué sobrevive a JSON.stringify

Todo lo que JSON no puede representar se transforma o desaparece **sin avisar**:

| Valor en JavaScript | Resultado en JSON | Al hacer `JSON.parse` |
|---|---|---|
| `Date` | string ISO (`"2026-01-03T12:30:00.000Z"`) | un string, no un `Date` |
| `undefined`, funciones, `Symbol` en una propiedad | la propiedad se omite | no existe |
| `undefined`, funciones, `Symbol` en un array | `null` | `null` |
| `NaN`, `Infinity`, `-Infinity` | `null` | `null` |
| `Map`, `Set` | `{}` (no tienen propiedades propias) | un objeto vacío |
| claves numéricas (`{ 1: "a" }`) | `{"1":"a"}` | la clave es el string `"1"` |
| instancias de clase | solo sus propiedades propias enumerables | objeto plano, sin métodos |
| `BigInt` | lanza `TypeError` | |

<Pregunta id="json-roundtrip-fecha-map" />

Ese es el primer bug: la API serializó el `Date` como string con `JSON.stringify` y `res.json()` te devolvió un string. Nadie lo convierte de vuelta salvo que tú lo hagas.

### replacer, space y reviver

`JSON.stringify(valor, replacer, space)` acepta dos argumentos más. `replacer` puede ser un array de claves permitidas (útil para no filtrar campos sensibles) o una función; `space` indenta la salida:

```js
JSON.stringify(user, ["id", "name"]);       // solo esas claves
JSON.stringify(config, null, 2);            // legible, con 2 espacios
```

`JSON.parse(texto, reviver)` llama a `reviver(clave, valor)` para cada valor, de dentro hacia fuera y en todos los niveles; lo que devuelvas sustituye al valor. Es la forma de **revivir las fechas**:

```js
const order = JSON.parse(text, (key, value) =>
  key === "createdAt" && typeof value === "string" ? new Date(value) : value,
);
order.createdAt.getTime(); // ahora sí
```

En aplicaciones grandes esto suele hacerse en la capa de datos (un esquema de Zod con `z.coerce.date()`, por ejemplo), pero el mecanismo es el mismo: alguien tiene que convertir el string de vuelta.

### JSON.parse lanza

Con un texto inválido, `JSON.parse` lanza `SyntaxError`. Si los datos vienen de `localStorage`, de una URL o de cualquier sitio que el usuario (o una versión antigua de tu app) puede haber dejado corrupto, envuélvelo en `try/catch` y devuelve un valor por defecto. Un detalle: `getItem` devuelve `null` si la clave no existe, y `JSON.parse(null)` no lanza, devuelve `null` (convierte `null` al texto `"null"`).

<Callout type="cuidado">
Comparar objetos con `JSON.stringify(a) === JSON.stringify(b)` es frágil: el resultado depende del **orden de las claves** (`{ a: 1, b: 2 }` y `{ b: 2, a: 1 }` dan strings distintos), y además ignora todo lo que JSON pierde (`{ x: undefined }` sale igual que `{}`, y `NaN` igual que `null`). Sirve para un test rápido, no como igualdad profunda. Y `JSON.parse(JSON.stringify(x))` como "copia profunda" pierde fechas, Maps y `undefined`: para eso existe `structuredClone`.
</Callout>

## Qué cruza del servidor al cliente

En Next.js, los datos pasan del servidor al navegador serializados. Qué se puede pasar depende del canal:

- **Respuestas HTTP** (Route Handlers, APIs externas, `fetch` + `res.json()`): JSON puro. Todo lo de la tabla anterior aplica.
- **Pages Router** (`getServerSideProps`, `getStaticProps`): las props deben poder serializarse con `JSON.stringify`. Devolver un `Date` da un error de serialización y hay que convertirlo a string antes.
- **App Router** (props de un Server Component a un Client Component): React usa su propio formato, más rico que JSON, que sí admite `Date`, `Map`, `Set`, `undefined` o `BigInt`. Pero no admite funciones normales (solo Server Functions) ni instancias de clases propias: un `onClick` no puede cruzar.

<Callout type="clave">
Cada vez que un dato cruza una frontera (red, almacenamiento, servidor → cliente), pregúntate qué formato de serialización usa y qué tipos se pierden. La respuesta casi siempre es "JSON, así que fechas → strings".
</Callout>

## Resumen

- **Punto** para nombres literales; **corchetes** cuando la clave está en una variable, se calcula o no es un identificador válido. `{ [clave]: valor }` calcula la clave en un literal.
- Una propiedad que no existe da `undefined`; el `TypeError` llega al leer algo **de** ese `undefined`. `in` distingue "no existe" de "vale `undefined`"; `delete` elimina la propiedad.
- `length` se puede asignar y trunca el array en sitio; `at(-1)` lee el último; `Array.isArray` es la forma fiable de detectar un array.
- `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse` y `fill` **mutan**. `slice`, `concat`, `toSorted`, `toReversed`, `toSpliced` y `with` devuelven uno nuevo. Mira también qué devuelve cada uno.
- `includes` encuentra `NaN`; `indexOf` no.
- JSON solo tiene strings, números finitos, booleanos, `null`, arrays y objetos: las fechas vuelven como strings, `Map`/`Set` como `{}`, `NaN`/`Infinity` como `null`, y `undefined`/funciones desaparecen. Revive con un `reviver` y protege `JSON.parse` con `try/catch`.
