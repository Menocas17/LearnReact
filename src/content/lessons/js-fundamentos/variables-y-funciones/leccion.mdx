## Un refactor "que no cambiaba nada"

Ayer se aprobó un PR: *"Paso los callbacks a arrow functions, que es lo mismo pero más corto, y
quito una arrow que sobraba en el botón"*. Hoy hay un ticket:

> **#273 — "Desde el refactor, la lista de tareas sale vacía".** No hay ningún error en consola.
> Con el arreglo rápido que se subió esta mañana las tareas sí aparecen… y se borran solas, sin
> que nadie pulse "Borrar".

El cambio en la lista:

```jsx
// antes
{items.map(function (item) {
  return <TodoItem key={item.id} item={item} onDelete={onDelete} />;
})}

// después del refactor
{items.map((item) => {
  <TodoItem key={item.id} item={item} onDelete={onDelete} />;
})}
```

El arreglo rápido devolvió el `return` y dejó a la vista el cambio del botón en `TodoItem`:

```jsx
// antes
<button onClick={() => onDelete(item.id)}>Borrar</button>

// después del refactor
<button onClick={onDelete(item.id)}>Borrar</button>
```

Ahora cada tarea se borra **al renderizar la lista**, sin que nadie haga clic (y, en desarrollo,
React avisa de que se actualiza un componente mientras se renderiza otro). Tres preguntas:

1. ¿Por qué un `map` que claramente escribe un `<TodoItem>` por tarea devuelve una lista vacía, y
   sin un solo error?
2. ¿Por qué el botón borra sin clic, si lo único que se quitó fue "una arrow que sobraba"?
3. ¿Es verdad que una arrow function es "lo mismo, pero más corta"?

Ninguna es un problema de React: son reglas de JavaScript, y tienen historia.

## Dos épocas en el mismo lenguaje

Durante sus primeros veinte años, el estándar de JavaScript tuvo una sola forma de declarar
variables (`var`) y una sola palabra para escribir funciones (`function`). La edición de 2015 del estándar (ECMAScript
2015, también llamada ES6) añadió de golpe casi todo lo que usas a diario: `let`, `const`, las
arrow functions, los parámetros por defecto y los parámetros rest.

¿Por qué *añadir* en lugar de *arreglar*? Porque la web no se puede romper: muchísimas páginas
dependen de cómo se comporta `var`, rarezas incluidas. La salida fue crear palabras nuevas con
reglas mejores y dejar las viejas como estaban.

## La mesa de trabajo

La imagen de toda la lección: tu programa es una **mesa de trabajo** llena de **valores**
(números, strings, objetos, arrays). **Las variables son etiquetas** con un nombre, atadas con un
hilo a un valor de la mesa. La etiqueta no *es* el valor: solo te permite encontrarlo.

- `const`: la etiqueta va atada con nudo ciego. No la puedes desatar para atarla a otro valor. Es
  la opción por defecto.
- `let`: la puedes desatar y atar a otro valor. Úsala cuando de verdad cambia (un acumulador, un
  índice).
- `var`: la etiqueta de la época anterior. Su alcance es la función entera en lugar del bloque y
  tiene rarezas de hoisting. En código moderno no se usa.

`let` y `const` tienen **alcance de bloque**: la etiqueta solo existe dentro de las llaves donde
se declara (un `if`, un `for`, una función).

<AntesDeSeguir>

¿Qué imprime esto?

```js
if (true) {
  var a = 1;
  let b = 2;
}
console.log(typeof a, typeof b);
```

<Respuesta>

```
number undefined
```

`a` se declaró con `var`, que ignora las llaves del `if`: la etiqueta pertenece a la función que
lo contiene (o al nivel superior del archivo). `b` desaparece al cerrar la llave, y `typeof` sobre un nombre que no existe
devuelve `"undefined"` en lugar de lanzar. El detalle de scope, hoisting y por qué usar `let` o
`const` antes de su línea lanza un error está en la lección «Scope y hoisting» del módulo 3.

</Respuesta>

</AntesDeSeguir>

### Reasignar no es mutar

Aquí está el detalle que más confunde. El nudo de `const` protege el **hilo** (a qué valor
apunta la etiqueta), no el **valor**. Si el valor es un objeto o un array, nada te impide
cambiar lo que hay dentro:

```js
const user = { name: "Ana" };
user.name = "Luis";     // ✅ muta el objeto: const no lo impide
user = { name: "Eva" }; // ❌ TypeError: Assignment to constant variable.
```

<AntesDeSeguir>

Dos etiquetas, un solo array. ¿Qué imprime?

```js
const tareas = ["leer"];
let otras = tareas;
otras.push("escribir");
otras = ["dormir"];
console.log(tareas.join(","));
console.log(otras.join(","));
```

<Respuesta>

```
leer,escribir
dormir
```

`let otras = tareas` no copia nada: ata otra etiqueta **al mismo** array, y el `push` lo cambia
para las dos. Luego `otras = ["dormir"]` desata `otras` y la ata a un array nuevo.

</Respuesta>

</AntesDeSeguir>

Esta pregunta pone a prueba justo la diferencia entre las dos operaciones, con un `try/catch`
para ver qué lanza la reasignación:

<Pregunta id="variables-const-mutar" />

En React esto importa dos veces. Casi todo es `const` en un componente porque cada render es una
**llamada nueva** a la función: `const [count, setCount] = useState(0)` crea etiquetas nuevas
cada vez, y en lugar de reasignar `count` pides un render nuevo con `setCount`. Y `const` **no te
protege** del bug clásico:

```jsx
const [todos, setTodos] = useState([]);

function add(todo) {
  todos.push(todo); // muta el array del estado: const no se queja
  setTodos(todos);  // mismo array → React cree que no cambió nada
}
```

La solución es crear un array nuevo (`setTodos([...todos, todo])`); lo verás a fondo en la
lección «Valores y referencias» del módulo 3.

<Callout type="nota">
Para congelar el contenido de verdad existe `Object.freeze`, pero es superficial y en la práctica casi no se usa: la convención en React es simplemente no mutar.
</Callout>

## Las máquinas también están en la mesa

Segunda capa. **Una función es una máquina**: ranuras de entrada (los parámetros), un botón
(llamarla) y una bandeja de salida (lo que devuelve). Y la máquina es un valor más de la mesa:
puedes atarle una etiqueta, guardarla en un cajón, dársela a otra máquina o sacarla de la bandeja
de otra:

```js
const handlers = { save: () => "guardado" };     // guardada en un objeto
[3, 1, 2].sort((a, b) => a - b);                  // pasada como argumento
const greet = (greeting) => (name) => greeting + ", " + name; // devuelta
greet("Hola")("Ana"); // "Hola, Ana"
```

(Que `greet("Hola")` recuerde `greeting` después de terminar es un closure; lo tienes en el
módulo 3.) Las funciones como valores vienen de la influencia de Scheme, un dialecto de Lisp que Eich
admiraba y que marcó el diseño original de JavaScript, y son la base de React: componentes, handlers, efectos.

Hay tres formas de fabricar una máquina:

```js
// Declaración: tiene nombre y se puede usar antes de la línea donde aparece
function add(a, b) {
  return a + b;
}

// Expresión: una función como valor asignado a una variable
const sub = function (a, b) {
  return a - b;
};

// Arrow function: expresión más corta
const mul = (a, b) => a * b;
```

<AntesDeSeguir>

¿Qué imprime este script?

```js
console.log(sumar(2, 3));

function sumar(a, b) {
  return a + b;
}

try {
  console.log(restar(5, 1));
} catch (e) {

```


Las **declaraciones** se preparan antes de ejecutar el código (hoisting): puedes llamarlas antes
de su línea. Las expresiones y las arrows no: son una `const` como cualquier otra, inutilizable
hasta que se ejecuta su línea (la *TDZ*, que verás a fondo en el módulo 3).

</Respuesta>

</AntesDeSeguir>

Las otras diferencias que importan en el día a día son de las arrows:

- **No tienen `this` ni `arguments` propios**: usan los de la función donde se escribieron. Por
  eso son las cómodas para callbacks. El detalle de `this` está en su propia lección, «this», del módulo 3.
- **No se pueden usar con `new`.**

<Profundiza titulo="por qué las arrows no tienen this propio">

Antes de 2015, un callback escrito con `function` dentro de un método recibía su propio `this`,
casi nunca el que querías, y el código se llenaba de parches como `var self = this;` o
`.bind(this)`. Las arrows no crean su propio `this` y usan el del código que las rodea, así que
el parche sobra. A cambio, no sirven como constructores ni como métodos que necesiten su `this`.

</Profundiza>

En componentes de React verás las dos convenciones (`function Button()` y
`const Button = () =>`); para lo que hace React son equivalentes.

## La bandeja de salida

Tercera capa: ¿qué sale por la bandeja? Una arrow tiene dos formas de cuerpo:

```js
const double = (n) => n * 2;              // cuerpo de expresión: devuelve n * 2
const double2 = (n) => { n * 2; };        // cuerpo de bloque: evalúa y DESCARTA → undefined
const double3 = (n) => { return n * 2; }; // bloque con return explícito
```

Con **cuerpo de expresión**, lo que escribes tras la flecha va directo a la bandeja. Con **cuerpo
de bloque** hay un taller dentro, y de él solo sale lo que pongas con `return`. La regla:

> **Si después de `=>` hay una llave, es un bloque**, y un bloque solo devuelve algo con
> `return`. Una función sin `return` (o con `return;` a secas) devuelve `undefined`.

<AntesDeSeguir>

¿Qué imprime?

```js
const a = [1, 2].map((n) => n * 2);
const b = [1, 2].map((n) => {
  n * 2;
});
console.log(a.join(" "));
console.log(b.length, b[0]);
```

<Respuesta>

```
2 4
2 undefined
```

`map` llamó al callback dos veces en ambos casos, pero en `b` el taller calculó `n * 2`, lo tiró
y no puso nada en la bandeja: cada vuelta devolvió `undefined`, sin ningún error.

</Respuesta>

</AntesDeSeguir>

### La trampa del objeto

La misma regla produce la trampa del objeto literal: `() => { a: 1 }` **no** devuelve un objeto.
Las llaves abren un bloque, `a:` se interpreta como una etiqueta (*label*, una sintaxis antigua y
casi olvidada, usada sobre todo para nombrar bucles) y `1` es una expresión que se descarta. Para
devolver un objeto con return implícito, envuélvelo en paréntesis: `() => ({ a: 1 })`.

<Profundiza titulo="por qué la llave gana siempre">

La gramática de ECMAScript lo decide por adelantado: el cuerpo conciso de una arrow
(*ConciseBody*) solo se lee como expresión si **no** empieza por `{`. Lo mismo vale para una
sentencia suelta, que nunca puede empezar por `{` como expresión. El parser no "adivina" por lo
que viene después: `{ id }` tras la flecha es un bloque aunque parezca un objeto abreviado.

</Profundiza>

Esta pregunta compara llaves, paréntesis y `return` sobre el mismo `map`:

<Pregunta id="funciones-arrow-objeto" />

<Callout type="cuidado">
`() => { a: 1, b: 2 }` ni siquiera compila: lanza un `SyntaxError`, porque `b: 2` no es válido como expresión. Si ves un error raro en una arrow que devuelve un objeto, busca los paréntesis que faltan. Típico en reducers, `setState((prev) => ({ ...prev, x }))` y `map` que transforma a objetos.
</Callout>

Con esto, los arreglos posibles del `map` del ticket son tres:

```jsx
{items.map((item) => <TodoItem key={item.id} item={item} />)}   // return implícito
{items.map((item) => (
  <TodoItem key={item.id} item={item} />                          // paréntesis para varias líneas
))}
{items.map((item) => {
  const done = item.status === "done";
  return <TodoItem key={item.id} item={item} done={done} />;      // bloque + return
})}
```

## Las ranuras de entrada

Cuarta capa: lo que entra en la máquina. Una ranura puede tener un **repuesto** para cuando llega
vacía:

```js
function createUser(name, role = "viewer") {
  return { name, role };
}
```

Dos reglas que no son obvias:

1. **El repuesto solo se usa si la ranura llega vacía, y vacía significa `undefined`.** Omitir el
   argumento o pasar `undefined` activan el valor por defecto; `null`, `0`, `""` o `false` son
   piezas reales y se respetan. Esto muerde con APIs que devuelven `null` para "sin valor":
   `createUser("Ana", null)` crea un usuario con `role: null`.
2. **El repuesto se fabrica en cada llamada**, en el momento de la llamada. `list = []` crea un
   array nuevo cada vez (al contrario que en Python, donde el valor por defecto se evalúa una sola
   vez al definir la función y se comparte), e `id = nextId()` llama a `nextId` solo cuando hace
   falta. Puede incluso usar parámetros anteriores: `function range(start, end = start + 10)`.

Ojo con el matiz de la segunda regla: el repuesto es nuevo en cada llamada **si es una expresión
que crea algo** (`[]`, `{}`). Si es una etiqueta atada a un array que ya existe
(`tags = DEFAULT_TAGS`), todas las llamadas reciben **ese mismo** array, y mutarlo lo cambia para
todas (y cambia la constante, que `const` no impide). Lo arreglarás en el primer ejercicio.

### La tolva del final: rest params

`...nombre` como último parámetro es una tolva que recoge los argumentos restantes en un **array
de verdad**:

```js
function log(level, ...messages) {
  console.log("[" + level + "]", messages.join(" "));
}
log("info", "servidor", "listo"); // [info] servidor listo
```

Antes de 2015 solo existía `arguments`, un objeto *parecido* a un array (con `length` e índices,
sin `map` ni `reduce`) y solo en funciones normales. Usa rest params: son un array y funcionan en
arrows.

## Dar la máquina o dar lo que sale de ella

Última capa. Si las funciones son valores, puedes entregar dos cosas muy distintas:

- `handleClick` es **la máquina**, un valor que todavía no ha hecho nada.
- `handleClick()` es **pulsar el botón ahora** y quedarte con lo que sale por la bandeja.

En JSX, lo que va entre llaves se evalúa **durante el render**. `onClick={handleClick}` le da a
React la máquina para que la pulse cuando haya un clic. `onClick={handleClick()}` la pulsa en cada
render y le pasa a React lo que salió (normalmente `undefined`). Si necesitas pasar argumentos,
envuélvela en otra máquina que todavía no se ha pulsado: `onClick={() => handleDelete(item.id)}`.

Esta pregunta imita lo que hace React con `onClick` sin React de por medio: comprueba cuándo se
ejecuta cada handler.

<Callout type="clave">

### Máquinas que no tocan la mesa

Una función es **pura** si con los mismos argumentos devuelve siempre lo mismo y no cambia nada
fuera de ella: solo mira sus ranuras y solo escribe en su bandeja (no muta sus argumentos, no
escribe variables externas, no hace peticiones). React espera eso de tus componentes durante el
render; por eso `todos.push(...)` en un componente es un problema y `createTask` del ejercicio no
debe mutar el array que recibe. El tema completo está en el módulo 6, «Programación funcional y patrones».

## El ticket, resuelto

**¿Por qué la lista sale vacía sin un error?** Tras la flecha del `map` hay una llave: es un
bloque. El `<TodoItem>` se construye, nadie lo pone en la bandeja con `return` y se descarta. El
`map` devuelve `[undefined, undefined, …]`, y React ignora `undefined` en una lista sin quejarse.

**¿Por qué el botón borra sin clic?** Porque la arrow no sobraba: era la máquina sin pulsar. Sin
ella, `onDelete(item.id)` se ejecuta al construir las props.

<AntesDeSeguir>

El compilador de JSX convierte cada elemento en una llamada con un objeto de props (algo como
`jsx("button", { onClick: … })`). Con una imitación mínima, ¿qué imprime?

```js
// imitación mínima de lo que produce el compilador de JSX
const jsx = (type, props) => ({ type, props });

const borrados = [];
const onDelete = (id) => {
  borrados.push(id);
};

const items = [{ id: 1 }, { id: 2 }];
const botones = items.map((item) => jsx("button", { onClick: onDelete(item.id) }));

console.log(borrados.join(","));
console.log(typeof botones[0].props.onClick);
```

<Respuesta>

```
1,2
undefined
```

Construir el objeto de props obliga a evaluar cada valor, y evaluar `onDelete(item.id)` es pulsar
el botón: las tareas se borran mientras se construye la lista, y `onClick` queda en `undefined`.

</Respuesta>

</AntesDeSeguir>

**¿Es una arrow "lo mismo, pero más corta"?** Casi, pero no: la llave cambia lo que sale por la
bandeja, no se puede llamar antes de su línea, no tiene `this` ni `arguments` propios y no sirve
con `new`. Y quitar una arrow nunca es cosmético: cambia "una máquina" por "lo que sale de ella".

## Lo que ahora puedes explicar

Si alguien dice "`const` significa que no cambia", ahora sabes precisarlo: no cambia **a qué**
está atada la etiqueta, pero lo que hay al otro lado del hilo se puede mutar, y en el estado de
React eso es un bug. Sabes que una llave tras `=>` abre un taller del que solo sale lo que pongas
con `return`, que un repuesto solo entra con `undefined` y se fabrica en cada llamada, que
`...rest` te da un array de verdad, y a leer cada `onClick` preguntándote si le das a React la
máquina o lo que salió de ella.

La siguiente lección mira de cerca las piezas más comunes de la mesa, strings, números y fechas,
con sus propias trampas: un total con diecisiete decimales y una cita que aparece un día antes.
