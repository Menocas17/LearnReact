## El bug

Dos tickets que llegan tarde o temprano a cualquier app con carrito o con fechas:

```jsx
function Total({ items }) {
  const total = items.reduce((sum, item) => sum + item.price, 0);
  return <p>Total: {total} €</p>; // "Total: 0.30000000000000004 €"
}

function Cita({ fecha }) {
  // fecha = "2026-10-14", guardada desde un <input type="date">
  return <p>{new Date(fecha).toLocaleDateString()}</p>; // en México: "13/10/2026"
}
```

En tu máquina todo se veía bien; en producción el total tiene 17 decimales y la cita aparece **un día antes**. Ninguno de los dos es un bug de React: son reglas de JavaScript sobre números y fechas que casi nadie lee hasta que le muerden. Vamos a recorrerlas, empezando por los strings, que tienen menos trampas pero las tienen.

## Strings

### Template literals

Ya los usas: entre backticks puedes interpolar **cualquier expresión** con `${…}`, no solo variables, y escribir varias líneas.

```js
const qty = 3;
const msg = `Tienes ${qty} ${qty === 1 ? "artículo" : "artículos"} (${(qty * 4.5).toFixed(2)} €)`;
```

Detalle útil: lo interpolado se convierte con `String(valor)`. Por eso `${null}` imprime `"null"` y `${obj}` imprime `"[object Object]"`: si ves eso en la UI, estás interpolando algo que no es lo que crees.

### Son inmutables

Ningún método de string modifica el original: **todos devuelven un string nuevo**. `name.trim()` en una línea suelta no hace nada útil. Es el mismo modelo mental que el estado de React: no se muta, se reemplaza.

<Pregunta id="strings-inmutables-at" />

### Los métodos que vas a usar

```js
const s = "  Hola, Mundo  ";
s.trim();                    // "Hola, Mundo" (también trimStart / trimEnd)
"react-hooks".split("-");    // ["react", "hooks"]
["a", "b"].join(" / ");      // "a / b"
"user".includes("se");       // true
"/admin/users".startsWith("/admin"); // true (y endsWith)
"7".padStart(3, "0");        // "007": ids, horas ("09:05")
"a.b.c".replaceAll(".", "/"); // "a/b/c" (replace con string solo cambia la primera)
"archivo.tar.gz".at(-1);      // "z"
```

Dos parejas que confunden:

- **`slice` vs `substring`**: los dos extraen un trozo `[inicio, fin)`. `slice` acepta negativos (`"hola".slice(-2)` es `"la"`); `substring` los trata como 0 y, si `inicio > fin`, los intercambia en silencio. Usa `slice` y olvídate del otro.
- **`at(-1)` vs `[-1]`**: los corchetes buscan una **propiedad** llamada `"-1"`, que no existe. Solo `at` cuenta desde el final.

`replace` con string reemplaza solo la primera aparición; para todas usa `replaceAll` o una regex con la bandera `g`.

### Ordenar con acentos y ñ

`sort()` sin comparador ordena por código UTF-16. En español eso es casi siempre incorrecto: mayúsculas antes que minúsculas y cualquier letra con tilde al final.

<Pregunta id="strings-ordenar-acentos" />

Para ordenar texto que lee una persona usa `localeCompare` con el idioma explícito, o `Intl.Collator` si vas a ordenar muchos elementos (crea el comparador una sola vez):

```js
users.toSorted((a, b) => a.name.localeCompare(b.name, "es"));

const collator = new Intl.Collator("es", { sensitivity: "base" });
users.toSorted((a, b) => collator.compare(a.name, b.name));
// sensitivity "base": "a", "A" y "á" se consideran iguales (útil para buscar)
```

### length y emojis

Un string es una secuencia de **unidades UTF-16**, y `length` cuenta esas unidades, no los caracteres que ve el usuario. La mayoría de letras ocupan una, pero los emojis ocupan dos (o más: `"👍🏽".length` es 4, porque es un emoji más un modificador de tono).

```js
"👍".length;        // 2
[..."👍"].length;   // 1: el spread itera por code points
"é".normalize("NFD").length; // 2: "e" + acento combinable
```

Consecuencias reales: un contador de "máximo 280 caracteres" que usa `length` penaliza los emojis, y un `slice(0, 10)` puede partir un emoji por la mitad y dejar un carácter roto. Si necesitas contar lo que el usuario percibe como caracteres, existe `Intl.Segmenter`; para el resto de casos, `length` está bien.

## Números

### Todo es un double

JavaScript solo tiene un tipo numérico de uso general, `number`: coma flotante de 64 bits (IEEE 754). No hay enteros "de verdad"; los enteros son doubles sin parte decimal. Y en binario, `0.1` es una fracción periódica (como 1/3 en decimal), así que se guarda **aproximada**:

```js
0.1 + 0.2;          // 0.30000000000000004
0.1 + 0.2 === 0.3;  // false
0.1 * 3;            // 0.30000000000000004
```

No es un bug de JavaScript: Python, Java o C dan exactamente lo mismo. Lo que cambia es cómo lo manejas.

### Dinero: trabaja en enteros

La regla práctica: **guarda y opera el dinero en la unidad mínima (céntimos) como entero**. Las sumas y multiplicaciones de enteros son exactas mientras no pasen de `Number.MAX_SAFE_INTEGER`. Conviertes a euros solo para mostrar.

```js
const toCents = (amount) => Math.round(amount * 100); // 19.99 * 100 = 1998.9999999999998 → 1999
const totalCents = items.reduce((t, i) => t + toCents(i.price) * i.qty, 0);
```

Mejor aún si los céntimos vienen así desde la base de datos o la API (Stripe, por ejemplo, trabaja en la unidad mínima de cada moneda). Y si tienes que comparar decimales que vienen de cálculos, no uses `===`: compara con una tolerancia. `Number.EPSILON` (unos 2.2e-16) es la distancia entre 1 y el siguiente double; sirve como tolerancia para valores cercanos a 1, pero para cantidades grandes necesitas una tolerancia proporcional al valor.

<Pregunta id="numeros-tofixed-epsilon" />

<Callout type="cuidado">
`toFixed` **devuelve un string**. `price.toFixed(2) + shipping` concatena en vez de sumar. Úsalo solo en el último paso, para mostrar, y nunca para redondear valores con los que vas a seguir calculando. Además redondea sobre el valor binario real: `(1.005).toFixed(2)` es `"1.00"`, porque 1.005 se guarda como 1.00499999…
</Callout>

### NaN e Infinity

- `NaN` ("not a number") es un `number` que resulta de operaciones sin sentido: `Number("abc")`, `0 / 0`, `undefined + 1`. Es **contagioso** (cualquier operación con `NaN` da `NaN`) y es el único valor que no es igual a sí mismo: `NaN === NaN` es `false`. Compruébalo con `Number.isNaN(x)`, no con `isNaN(x)` global, que convierte primero (`isNaN("abc")` es `true`).
- `1 / 0` es `Infinity`, no un error. Si un porcentaje muestra "Infinity %", dividiste entre un total de 0.

Un `NaN` en React suele verse como un "NaN" en pantalla o un input que se queda vacío: la pista es que algún `Number(...)` recibió `undefined` o un string con formato (`"1,5"`, `"12 €"`).

### Number() vs parseInt / parseFloat

Son dos filosofías distintas:

- `Number(str)` exige que **todo** el string sea un número (admite espacios alrededor y notación científica). Si no, `NaN`. Ojo: `Number("")` y `Number(null)` dan `0`, no `NaN`, así que un input vacío se convierte en 0 sin avisar.
- `parseInt(str, radix)` y `parseFloat(str)` leen **desde el principio** mientras encuentren dígitos válidos y descartan el resto: `parseInt("42px")` es 42, `parseFloat("3.14abc")` es 3.14.

```js
parseInt("101", 2);    // 5: el segundo argumento es la base (radix)
parseInt("08");        // 8 (en motores antiguos podía interpretarse como octal)
parseInt(0.0000005);   // 5 (!): el número se convierte primero a "5e-7"
["1", "2", "3"].map(parseInt); // [1, NaN, NaN]: map pasa (valor, índice) y el índice actúa como radix
```

Pasa siempre el radix (`parseInt(x, 10)`) y no le pases números. Para validar un formulario, `Number()` es más estricto y suele ser lo que quieres; `parseInt` es para extraer un número del principio de un texto. Si necesitas saber si es entero, `Number.isInteger(x)` (que no convierte: `Number.isInteger("5")` es `false`).

### Redondear con negativos

```js
Math.round(-2.5);  // -2: redondea los .5 hacia +∞, no "alejándose de cero"
Math.floor(-2.5);  // -3: siempre hacia abajo
Math.ceil(-2.5);   // -2: siempre hacia arriba
Math.trunc(-2.5);  // -2: quita los decimales
```

Con positivos `floor` y `trunc` coinciden, y por eso se intercambian sin pensar. Con negativos no: si calculas "días restantes" o una página a partir de una diferencia que puede ser negativa, elige a propósito.

### Enteros grandes y BigInt

Un double representa exactamente todos los enteros hasta `Number.MAX_SAFE_INTEGER` (2^53 − 1, unos 9 billones). Por encima, se saltan valores: `2 ** 53 + 1 === 2 ** 53` es `true`. El caso real: IDs de 64 bits (Twitter/X, Discord, algunas bases de datos) que llegan como número en un JSON y se corrompen en silencio al parsearlos. Por eso esas APIs los envían como **string**.

Para aritmética entera arbitraria existe `BigInt` (`10n`, `BigInt("9007199254740993")`), pero no se mezcla con `number` (`1n + 1` lanza `TypeError`) y `JSON.stringify` no lo serializa. En apps normales lo más habitual es tratar esos IDs como strings.

## Fechas

### Un Date es un instante

Un `Date` guarda **un solo número**: milisegundos desde el 1 de enero de 1970 a las 00:00 UTC (el *timestamp*, que obtienes con `getTime()` o `Date.now()`). No guarda zona horaria. Los métodos `getHours()`, `getDate()`, `toLocaleString()`… interpretan ese instante **en la zona del entorno** donde se ejecutan; los `getUTC*()` y `toISOString()` lo interpretan en UTC.

Las trampas clásicas:

```js
new Date(2026, 9, 14);   // 14 de OCTUBRE: los meses van de 0 a 11 (los días no)
new Date(Date.UTC(2026, 9, 14)); // mismo día, pero medianoche UTC en vez de local

new Date("2026-10-14");        // solo fecha → se interpreta como UTC
new Date("2026-10-14T00:00");  // fecha y hora sin zona → se interpreta como hora LOCAL
new Date("2026-10-14T00:00Z"); // con Z (u offset como -06:00) → instante exacto
```

Esa diferencia entre "solo fecha" (UTC) y "fecha con hora" (local) es una decisión histórica del estándar, y es la causa de muchos bugs de "el día anterior". Otros formatos (`"14/10/2026"`, `"Oct 14 2026"`) dependen del motor: no los parsees con `Date`.

### Date es mutable

Los setters (`setMonth`, `setDate`, `setHours`…) **modifican el objeto**. Si dos variables apuntan al mismo `Date`, cambiar una cambia la otra; y si mutas un `Date` que está en el estado de React, el componente no se entera (es el mismo objeto). Copia antes de modificar: `new Date(fecha)` o `new Date(fecha.getTime())`.

Además, los setters **desbordan** en lugar de fallar: el día 32 pasa al mes siguiente, el día 0 es el último del mes anterior, y "31 de enero + 1 mes" no es 28 de febrero.

<Pregunta id="fechas-mutable-desborde" />

### El bug del día anterior

Vuelve al componente `Cita`. `"2026-10-14"` se interpreta como **medianoche UTC**. Para un usuario en México (UTC−6), ese instante son las 18:00 del día **13**. `toLocaleDateString()` usa la zona del entorno, así que muestra el 13. En tu máquina en España (UTC+2) se veía el 14 y nadie lo notó.

<Pregunta id="fechas-dia-anterior" />

La solución depende de qué representa el dato:

- **Una fecha de calendario** (cumpleaños, fecha de una cita, "vence el 14"): no es un instante, no tiene zona. Lo más sencillo es tratarla como string `"YYYY-MM-DD"` y, cuando necesites `Date`, hacer todo en UTC: parsear como solo fecha, usar `getUTC*`/`setUTC*` y formatear con `timeZone: "UTC"`.
- **Un instante** (cuándo se hizo un pedido, cuándo se envió un mensaje): guárdalo en UTC (ISO con `Z` o timestamp) y conviértelo a la zona del usuario **solo al mostrarlo**.

<Callout type="clave">
Antes de tocar una fecha, pregúntate si es un **instante** o una **fecha de calendario**. Mezclarlos es el origen de casi todos los bugs de zonas horarias.
</Callout>

Y cuidado con calcular días restando timestamps en hora local: un cambio de horario de verano hace que un "día" dure 23 o 25 horas. Resta instantes UTC o redondea el resultado.

## Intl: formatear para personas

`Intl` formatea según el idioma y las convenciones de cada país, sin librerías. Crea el formateador una vez y reutilízalo; y pasa siempre el **locale** de forma explícita, porque si no usa el del entorno (el servidor o el navegador).

```js
const eur = new Intl.NumberFormat("es-ES", { style: "currency", currency: "EUR" });
eur.format(1999 / 100);  // "19,99 €"
new Intl.NumberFormat("es-MX", { style: "currency", currency: "MXN" }).format(1234.5); // "$1,234.50"
new Intl.NumberFormat("es-ES", { style: "percent", maximumFractionDigits: 1 }).format(0.256); // "25,6 %"

const fecha = new Intl.DateTimeFormat("es-MX", {
  dateStyle: "long",
  timeStyle: "short",
  timeZone: "America/Mexico_City",
});
fecha.format(new Date("2026-10-14T03:00:00Z")); // "13 de octubre de 2026, 9:00 p.m."

const rtf = new Intl.RelativeTimeFormat("es", { numeric: "auto" });
rtf.format(-1, "day");   // "ayer"
rtf.format(3, "hour");   // "dentro de 3 horas"

const pr = new Intl.PluralRules("es");
pr.select(1); // "one"
pr.select(5); // "other": eliges "artículo" o "artículos" según la categoría
```

Dos detalles prácticos:

- Algunos locales usan **espacios especiales** (U+00A0 o U+202F, sin salto de línea) entre el número y el símbolo, o antes de "p.m.". Visualmente son espacios, pero `"19,99 €" === eur.format(19.99)` puede dar `false`. En tests, normaliza con `.replace(/\s/g, " ")` o usa `formatToParts`.
- `RelativeTimeFormat` no calcula la diferencia: le das tú el número y la unidad ("hace 3 días" lo decides tú restando fechas).

### Hydration mismatch en Next.js

En Next.js un Client Component se renderiza **dos veces**: en el servidor (para generar el HTML) y en el navegador (al hidratar). Si formateas una fecha sin locale ni zona, cada entorno usa los suyos. Un servidor suele ejecutarse en UTC y en `en-US`; el navegador del usuario, en `America/Mexico_City` y `es-MX`. Los textos no coinciden y React avisa con un error de hidratación.

<Pregunta id="fechas-hydration-mismatch" />

Las salidas que tienes:

- **Fijar locale y zona** en el formateador (la zona del negocio, o la del usuario si la guardas en su perfil): servidor y cliente producen lo mismo.
- **Formatear solo en el cliente**, aceptando que el servidor muestre algo provisional; la guía de Next.js sobre *preventing flash before hydration* explica cómo corregirlo antes del primer pintado con un script inline.
- Para probar en local, arranca el servidor con otra zona: `TZ=UTC next dev` mientras tu navegador está en tu zona real. Si solo lo pruebas en tu máquina, el bug no aparece nunca.

### Temporal

`Date` tiene casi 30 años y arrastra decisiones que hoy nadie tomaría (mutable, meses desde 0, una sola clase para instantes y fechas de calendario). **Temporal** es la API que lo sustituye, con tipos separados como `Temporal.PlainDate` (fecha de calendario) o `Temporal.ZonedDateTime` (instante con zona), todos inmutables. Ya está disponible en algunos navegadores, pero no en Node 22; mientras no puedas contar con ella en todos tus entornos, aplica las reglas de esta lección con `Date` e `Intl` (o usa una librería como date-fns).

## Resumen

- Los strings son **inmutables**: sus métodos devuelven strings nuevos. Usa `slice`, `at(-1)`, `replaceAll` y ordena texto con `localeCompare`/`Intl.Collator` y un locale explícito.
- `length` cuenta unidades UTF-16: un emoji puede valer 2 o más.
- Todos los números son doubles: `0.1 + 0.2 !== 0.3`. El dinero se opera en **céntimos enteros** y se formatea al final.
- `toFixed` devuelve un string; `Number("")` es 0; `parseInt` lee hasta donde puede (pasa el radix); `round`, `floor` y `trunc` difieren con negativos.
- Por encima de `MAX_SAFE_INTEGER` los enteros pierden precisión: los IDs grandes van como string (o `BigInt`).
- Un `Date` es un instante en UTC; los meses van de 0 a 11 y los setters mutan y desbordan.
- `"2026-10-14"` es medianoche UTC; mostrarla en una zona al oeste de UTC da el **día anterior**. Distingue instantes de fechas de calendario.
- `Intl` formatea monedas, porcentajes, fechas, tiempos relativos y plurales. Pasa siempre locale y `timeZone` explícitos, sobre todo en código que se renderiza en servidor y cliente.
