## Un contador que se rinde en el 1

> **#214 — "La sala de espera dice que llevas 1 segundo... para siempre".** El contador sube a 1
> y ahí se queda.

Abres el componente, escrito como tantas veces:

```jsx
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <p>{count}</p>;
}
```

Un compañero propone cambiar `const` por `let` "para que `count` se pueda actualizar". No sirve.
Tres preguntas antes de tocar nada:

1. ¿Por qué el callback del intervalo ve siempre `0`, si la pantalla ya muestra `1`?
2. ¿Cómo puede seguir existiendo ese `count`, si la función `Timer` que lo creó terminó hace rato?
3. ¿Por qué `setCount((c) => c + 1)` lo arregla, si el callback sigue siendo el mismo?

No es un bug de React: es JavaScript haciendo exactamente lo que dice la especificación. La pieza
que falta se llama **closure**.

## Funciones que viajan

JavaScript trata las funciones como valores: las guardas en variables, las pasas a otras
funciones y las devuelves. Brendan Eich, su creador, llegó a Netscape con la idea de llevar al
navegador algo parecido a Scheme, un dialecto de Lisp; la sintaxis acabó pareciéndose a Java,
pero las funciones como valores vienen de esa tradición.

Eso abre una pregunta que los lenguajes de los años 60 tuvieron que resolver: si una función
viaja a otro sitio y se ejecuta más tarde, ¿dónde busca sus variables? Los Lisp de entonces solían
buscarlas **donde se ejecutaba** (*scope dinámico*): el resultado dependía de quién la llamara.
Scheme eligió lo contrario, buscarlas **donde se escribió** (*scope léxico*), y JavaScript
heredó esa decisión.

## Habitaciones con puerta

Esta imagen te acompaña toda la lección. Cada vez que **se llama** a una función,
JavaScript construye una **habitación** con sus parámetros y variables. Cada habitación tiene una
**puerta** que da a la habitación donde esa función **se escribió**, y así hasta el scope global.
Para encontrar un identificador, JavaScript mira en la habitación actual y, si no está, sale por
la puerta.

<AntesDeSeguir>

`leer` se llama desde dentro de `llamar`, que tiene su propio `nivel`. ¿Qué imprime?

```js
const nivel = "módulo";

function leer() {
  return nivel;
}

function llamar() {
  const nivel = "llamador";
  return leer();
}

console.log(llamar());
```

<Respuesta>

```
módulo
```

`leer` se escribió en el nivel del módulo, así que su puerta da al módulo, no a `llamar`. Quién
la llame no cambia dónde está la puerta. Eso es lo que significa **léxico**: la búsqueda depende
de dónde está escrito el código. Con scope dinámico, habría impreso `llamador`.

</Respuesta>

</AntesDeSeguir>

## La llave: qué es un closure

Segunda capa: una función creada dentro de una habitación **se lleva la llave** de esa habitación.
Un closure es eso: una función **junto con el entorno de variables donde fue creada**. Toda
función en JavaScript lo es, pero se nota cuando una se crea dentro de otra y sobrevive a ella:

```js
function createCounter() {
  let count = 0; // vive en la habitación de esta llamada
  return () => {
    count++; // la función devuelta tiene la llave
    return count;
  };
}
```

`createCounter` termina, pero la habitación no se derriba: sigue en pie mientras alguien tenga
la llave. Este es el porqué de segundo nivel: si las variables capturadas vivieran en la pila de llamadas,
desaparecerían con el `return` y devolver funciones sería imposible. Las variables capturadas
viven tanto como la función que las usa, y el recolector de basura solo las libera cuando nadie
puede alcanzarlas.

<AntesDeSeguir>

Con `createCounter` de arriba, ¿qué imprime esto?

```js
const a = createCounter();
const b = createCounter();
a();
a();
console.log(a(), b());
```

<Respuesta>

```
3 1
```

Cada llamada a `createCounter()` construye una habitación **nueva** con su propio `count`. `a` y
`b` tienen llaves de habitaciones distintas.

</Respuesta>

</AntesDeSeguir>

## Una llave, no una foto

Tercera capa: la llave abre la habitación; no es una foto de lo que había dentro. Un closure
guarda una referencia a la **variable**, no a su valor: si la variable cambia, el closure ve el
valor nuevo. Esta pregunta comprueba si lo crees de verdad:

## Cada render, una habitación nueva

Un componente de React es una función, y **cada render es una llamada nueva**: una habitación
nueva. En cada una, `useState` devuelve el valor de ese render y lo guardas en una `const`
**distinta**. Las funciones que creas durante el render (handlers, efectos, timeouts) se llevan la
llave de **esa** habitación.

Compruébalo sin React, con un `useState` de juguete:

<AntesDeSeguir>

¿Qué valor queda guardado tras tres ticks?

```js
let guardado = 0; // lo que React guarda entre renders
const setCount = (v) => {
  guardado = typeof v === "function" ? v(guardado) : v;
};

function Timer() {
  const count = guardado; // useState: el valor de ESTE render
  return () => setCount(count + 1); // callback del intervalo
}

const tick = Timer(); // render 1: el efecto crea el intervalo
tick();
Timer(); // render 2
tick();
Timer(); // render 3
tick();
console.log(guardado);
```

<Respuesta>

```
1
```

Los renders 2 y 3 construyen habitaciones nuevas con `count` en `1`, pero `tick` tiene la llave
de la habitación del render 1, donde `count` es `0` y nadie lo cambia. Por eso `let` no ayuda:
nadie reasigna esa variable; React no la modifica, **vuelve a llamar** a la función y crea otra.

</Respuesta>

</AntesDeSeguir>

## El ticket, resuelto

**¿Por qué ve siempre `0`?** En el render 1, el efecto (con `[]`, "solo al montar") crea el
intervalo, cuyo callback se lleva la llave del render 1. Cada segundo ejecuta `setCount(0 + 1)`.
React renderiza con `count = 1`, pero el efecto no se vuelve a ejecutar: el intervalo sigue con
el callback viejo. `setCount(1)`, `setCount(1)`… el valor ya es 1 y nada cambia. A esto se le
llama **closure obsoleta** (*stale closure*): una función que sigue viendo variables de un render
antiguo.

**¿Cómo sigue existiendo `count`?** Porque la habitación del render 1 sigue en pie mientras el
intervalo tenga la llave.

**¿Por qué lo arregla el updater?** Esta pregunta te pide elegir el cambio que funciona:

<Pregunta id="closures-fix-interval" />

Con `setCount((c) => c + 1)` el callback ya no lee `count`: React le pasa el valor más reciente.
El closure sigue siendo "viejo", pero ya no importa porque no depende de nada que cambie. La otra
salida es declarar `count` en las dependencias, y el intervalo se recrea en cada cambio.

## Llaves por todas partes

Los closures están detrás de mucho de lo que usas:

- **Estado privado**: como en `createCounter`, nadie toca `count` desde fuera.
- **Funciones fábrica**: `makeGreeter("Hola")` devuelve funciones configuradas.
- **Debounce, throttle y memoización**: guardan un timer o una caché entre llamadas.
- **Handlers en React**: cada `onClick={() => borrar(item.id)}` cierra sobre `item`.
- **Stores externos** (Zustand, por ejemplo): guardan estado y suscriptores en closures, como el
  `createStore` del patrón observer. Los callbacks que devuelven los custom hooks, en cambio,
  cierran sobre el estado de su render.

<Callout type="cuidado">
Un closure mantiene vivo todo lo que referencia. Si guardas un closure en un sitio de larga duración (un listener global, una caché) que captura objetos grandes, esos objetos no se liberan. Por eso los efectos limpian sus listeners.
</Callout>
