## La clase que React no deja jubilar

Escribes componentes con funciones y hooks desde hace años. Pero hay un sitio donde React 19 te
sigue pidiendo una clase: los **error boundaries**, los componentes que evitan que un error de
render tumbe toda la página. No hay hook equivalente; librerías como react-error-boundary o
`catchError` de Next.js te dan uno ya hecho, pero por dentro hay una clase. Y la de tu equipo
tiene un ticket:

> **#815 — "Un usuario inexistente muestra 'Algo salió mal'".** Al abrir `/usuarios/999` debería
> salir "Este usuario no existe". Sale el fallback genérico, y en el log el error aparece como
> `Error: No encontrado: /api/usuarios/999`.

```jsx
class NotFoundError extends Error {
  constructor(url) {
    super("No encontrado: " + url);
    this.url = url;
  }
}

class ErrorBoundary extends Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };
  }

  componentDidCatch(error, info) {
    logError(error.name + ": " + error.message, info.componentStack);
  }

  render() {
    const { error } = this.state;
    if (!error) return this.props.children;
    if (error.name === "NotFoundError") return <UsuarioNoExiste />;
    return this.props.fallback;
  }
}
```

En la revisión alguien pregunta por qué se comparan strings en vez de usar `instanceof`. El
autor responde: "En JavaScript las clases no son de verdad; prefiero no fiarme de `instanceof`".
Cuatro preguntas:

1. Si lanzaste un `NotFoundError`, ¿por qué `error.name` dice `"Error"`? ¿De dónde sale ese valor?
2. ¿Qué comprueba realmente `instanceof`? ¿Es fiable?
3. Tu clase no define `props` ni `setState`, y aun así `this.props` funciona y `this.setState`
   existiría. ¿De dónde salen?
4. ¿Por qué `getDerivedStateFromError` lleva `static`, `state = …` no y `render` tampoco? ¿Dónde
   acaba cada cosa?

## Un lenguaje sin moldes

En Java o C#, primero escribes una **clase**, un molde, y después fabricas objetos con él. El
molde existe aparte de los objetos, y qué métodos tiene cada objeto lo decide su clase.

Brendan Eich tomó otro camino para el modelo de objetos de JavaScript: el de **Self**, un
lenguaje experimental creado en los años 80 por David Ungar y Randall Smith. En Self no hay
clases, solo objetos. Cuando a un objeto le piden algo que no tiene, **delega** en otro objeto.
Un concepto en vez de dos.

Como viste en **Closures**, Netscape exigía que el lenguaje se pareciera a Java. El
resultado fue un híbrido: debajo, delegación al estilo Self; encima, `new` y funciones
constructoras con un aire familiar. Durante años, "hacer una clase" significó escribir una
función y colgar métodos de su `.prototype` a mano.

ES2015 añadió `class`, pero no cambió el modelo: MDN describe las clases como funciones
especiales construidas sobre prototipos. Lo que trajo fue una sintaxis común y algunas
protecciones. Los campos (`state = …`), los campos `static` y los miembros privados con `#`
llegaron más tarde, en ES2022; hasta entonces, la privacidad era una convención (`_saldo`) o un
closure.

El autor del ticket acierta: JavaScript **no tiene clases** como las de Java. Pero eso no hace
menos fiable a `instanceof`.

## Pregúntale a tu jefe

La imagen de esta lección: **cada objeto es un empleado de una oficina**. Tiene su propia
**libreta**, con lo que sabe él (sus propiedades), y exactamente **un jefe** al que preguntar lo
que no sabe. El jefe es otro objeto, con su libreta y su propio jefe, y así hasta el director,
que no tiene a nadie encima.

La especificación llama a ese enlace **`[[Prototype]]`**. No es una propiedad normal: se lee con
`Object.getPrototypeOf(obj)`. La forma más directa de contratar a un empleado con un jefe
concreto es `Object.create(jefe)`:

```js
const animal = {
  describe() {
    return this.name + " hace " + this.sound();
  },
  sound() {
    return "...";
  },
};

const rex = Object.create(animal); // libreta vacía, jefe: animal
rex.name = "Rex";

Object.getPrototypeOf(rex) === animal; // true
```

Cuando lees `rex.describe`, el motor hace esto:

1. ¿`rex` tiene en su libreta una propiedad **propia** llamada `describe`? Si sí, la devuelve.
2. Si no, le pregunta a su jefe, `Object.getPrototypeOf(rex)` (aquí, `animal`), y repite.
3. Sigue subiendo hasta llegar a `null`. Si nadie la tenía, el resultado es `undefined`.

```text
rex ──[[Prototype]]──▶ animal ──[[Prototype]]──▶ Object.prototype ──▶ null
 name                   describe, sound           toString, hasOwnProperty…
```

A esa lista se le llama **cadena de prototipos**. `Object.prototype` es el director, jefe por
defecto de los objetos literales. No se copia nada; se **enlaza**.

<AntesDeSeguir>

`rex` no tiene `describe` en su libreta. ¿Qué imprime?

```js
console.log(rex.describe());
console.log(animal.describe());
```

<Respuesta>

```
Rex hace ...
undefined hace ...
```

El jefe le dice a `rex` **cómo** describirse, pero lo hace `rex` con su propia libreta: como
viste en la lección **this**, `this` es el objeto antes del punto, aunque la función se haya
encontrado un piso más arriba. Por eso un único `describe` sirve para todos.
Llamado sobre `animal`, `this` es `animal`, que no tiene `name`.

</Respuesta>

</AntesDeSeguir>

### Lo que sabes tú y lo que sabe tu jefe

Una propiedad **propia** está en la libreta del objeto; una **heredada** se encuentra
preguntando hacia arriba. Hay herramientas para cada pregunta.

<AntesDeSeguir>

Con el mismo `rex`, ¿qué imprime?

```js
console.log(Object.hasOwn(rex, "name"), Object.hasOwn(rex, "describe"));
console.log("describe" in rex, "toString" in rex);
console.log(Object.keys(rex).join(","));
```

<Respuesta>

```
true false
true true
name
```

`Object.hasOwn` solo mira la libreta; `in` pregunta a toda la cadena, hasta el director, que
sabe `toString`. `Object.keys` devuelve solo las propias (y enumerables).

</Respuesta>

</AntesDeSeguir>

`Object.hasOwn` es la versión moderna de `obj.hasOwnProperty(key)`, que es un método que el
objeto tiene que **encontrar** en su cadena: falla con un empleado sin jefe (`Object.create(null)`)
o con uno que tape `hasOwnProperty`. `Object.hasOwn` funciona siempre.

## Leer sube, escribir no

Segunda capa, y la fuente de casi todas las sorpresas: **preguntar** sube por la cadena, pero
**anotar** no. Asignar (`obj.x = …`) escribe en la libreta de `obj`; nunca en la del jefe.

Si anotas algo que el jefe ya sabía, tu nota **tapa** la suya: a partir de ahí respondes tú. Se
llama *shadowing*. Si la borras con `delete`, vuelve a responder el jefe. Esta pregunta pone a
prueba esas tres fases:

<Pregunta id="prototipos-shadowing-delete" />

Ahora el caso venenoso. Imagina que el jefe tiene una pizarra en su despacho.
`a.tags.push("js")` **no** es anotar `tags` en la libreta de `a`: es preguntar "¿dónde está
`tags`?" (una lectura, que sube hasta el jefe) y escribir en la pizarra que te señalan, la del
jefe, que ven todos sus empleados. Esta pregunta mezcla las dos operaciones:

<Pregunta id="prototipos-array-compartido" />

<Callout type="cuidado">
Nunca pongas estado mutable (arrays, objetos) en un prototipo: lo comparten todas las instancias, y un `push` desde una se ve en todas. Los prototipos son para **comportamiento** (métodos); los datos van en cada instancia. Las clases hacen esto bien por defecto, como verás enseguida.
</Callout>

### La excepción: el jefe que quiere enterarse

Anotar no escribe en tu libreta cuando más arriba en la cadena hay un **setter** para esa
propiedad. Es como si el jefe hubiera dejado dicho "si alguien quiere anotar
`nombre`, que me lo pase a mí". La asignación ejecuta el setter en lugar de crear la propiedad.

<AntesDeSeguir>

¿Qué imprime?

```js
const perfil = {
  set nombre(valor) {
    this._nombre = valor.trim();
  },
  get nombre() {
    return this._nombre;
  },
};
const ana = Object.create(perfil);
ana.nombre = "  Ana  ";
console.log(Object.hasOwn(ana, "nombre"), Object.hasOwn(ana, "_nombre"));
console.log("[" + ana.nombre + "]");
```

<Respuesta>

```
false true
[Ana]
```

`ana.nombre = …` encontró el setter en `perfil` y lo ejecutó con `this` igual a `ana`. Por eso
`nombre` no aparece en la libreta de `ana`, pero `_nombre` sí: el setter lo anotó en la libreta
de quien preguntó, no en la del jefe.

</Respuesta>

</AntesDeSeguir>

## Por qué todos los arrays tienen map

Nunca has definido `map` en tus arrays y siempre está ahí. Cuando escribes `[1, 2]`, el motor
contrata un empleado cuyo jefe es `Array.prototype`, y ahí viven `map`, `filter`, `push`… una
sola vez, compartidos por todos los arrays del programa.

```text
[1, 2] ──▶ Array.prototype ──▶ Object.prototype ──▶ null
           map, filter, push…   toString, hasOwnProperty…
```

Igual con las funciones (`Function.prototype.call`, `bind`), los strings
(`String.prototype.toUpperCase`) o las promesas (`Promise.prototype.then`).

Aquí aparece una confusión de nombres que conviene aclarar ya:

- **`[[Prototype]]`** es el enlace de *cualquier* objeto con su jefe. Se lee con
  `Object.getPrototypeOf`.
- **`.prototype`** es una propiedad normal que tienen las *funciones* (constructoras y clases).
  Es el jefe que se asignará a lo que esa función cree con `new`.

`Array.prototype` no es el jefe de `Array`; es el jefe **de los arrays**. Esta pregunta pone a
prueba justo esa distinción:

<Pregunta id="prototipos-metodos-array" />

<Profundiza titulo="por qué no se tocan los prototipos ajenos">

Como todos los arrays comparten jefe, añadir un método a `Array.prototype` se lo da a todos los
arrays del programa, incluidos los de librerías que no esperaban encontrarlo. Algunas librerías
antiguas lo hacían. MooTools, por ejemplo, añadía su propio `Array.prototype.flatten`, y cuando
el comité de JavaScript (TC39) quiso estandarizar un método con ese nombre, se descubrió que
rompía páginas que aún usaban MooTools. El método acabó llamándose `flat`.

</Profundiza>

## new: el departamento de contratación

Tercera capa. Antes de `class`, las "clases" se escribían con funciones constructoras, y sigue
siendo exactamente lo que pasa por debajo. Una función constructora es un **departamento de
contratación**: su `.prototype` es el jefe que asigna a cada contratado.

```js
function Dog(name) {
  this.name = name; // dato: en la libreta de cada instancia
}
Dog.prototype.bark = function () {
  return this.name + ": guau"; // método: una vez, en el jefe común
};

const rex = new Dog("Rex");
```

`new Dog("Rex")` hace, en resumen:

1. Crea un objeto vacío cuyo `[[Prototype]]` es `Dog.prototype`.
2. Ejecuta `Dog` con `this` apuntando a ese objeto.
3. Devuelve el objeto (salvo que la función devuelva otro objeto explícitamente).

<AntesDeSeguir>

¿Qué imprime?

```js
console.log(rex.bark());
console.log(Object.getPrototypeOf(rex) === Dog.prototype, Object.hasOwn(rex, "bark"));
```

<Respuesta>

```
Rex: guau
true false
```

`bark` vive en el jefe común, `Dog.prototype`; en la libreta de `rex` solo está `name`.

</Respuesta>

</AntesDeSeguir>

El punto débil de esta forma es que `Dog` sigue siendo una función normal, y nada te impide
llamarla sin `new`. En código no estricto, `this` era el objeto global y `Dog("Toby")` escribía
`name` en el objeto global, en silencio; en modo estricto, `this` es `undefined` y lanza `TypeError`.

## class: el mismo departamento, con un formulario mejor

Ahora la versión con `class`, que hace lo mismo:

```js
class Dog {
  constructor(name) {
    this.name = name;
  }
  bark() {
    return this.name + ": guau";
  }
}
```

<AntesDeSeguir>

¿Qué imprime?

```js
console.log(typeof Dog, Dog.prototype.constructor === Dog);
console.log(Object.getOwnPropertyNames(Dog.prototype).join(","));
console.log(Object.keys(Dog.prototype).length);
```

<Respuesta>

```
function true
constructor,bark
0
```

Una clase **es una función**: el `constructor` es su cuerpo y los métodos se colocan en
`Dog.prototype`, que además apunta de vuelta a la clase con `constructor`. `Object.keys` da `0`
porque los métodos de una clase **no son enumerables**: no aparecen al recorrer las claves.

</Respuesta>

</AntesDeSeguir>

Es una de las tres cosas que añade `class`. Las otras: no se puede llamar sin `new` (lanza
`TypeError` siempre) y su cuerpo siempre está en modo estricto.

Dentro de una clase hay varios sitios donde pueden acabar las cosas. En la oficina: en el jefe
común, en la libreta de cada empleado o en el propio departamento.

| Sintaxis | Dónde vive |
|---|---|
| `metodo() { … }` | En `Clase.prototype`, compartido |
| `get x() { … }` / `set x(v) { … }` | En `Clase.prototype`, compartido |
| `campo = valor` | En **cada instancia**, se crea al construirla |
| `static algo` | En la propia clase (la función), no en las instancias |
| `#privado` | Campos: en cada instancia; métodos `#m()`: compartidos. Inaccesible desde fuera de la clase |

Ya viste en la lección **this** que un campo arrow y un método se comportan distinto. Con la
tabla delante, esta pregunta te pide decir **dónde** vive cada uno:

<Pregunta id="clases-metodo-vs-campo-arrow" />

En class components verás `handleClick = () => { … }` justo por esto: un campo arrow captura el
`this` de la instancia y no se pierde al pasarlo como `onClick`. El precio es una función nueva
por instancia, anotada en cada libreta en vez de una sola en el jefe.

### Privados, static, getters y setters

```js
class Cuenta {
  #saldo = 0; // privado: solo accesible dentro del cuerpo de la clase
  static comision = 0.01; // de la clase: Cuenta.comision

  get saldo() {
    return this.#saldo; // se lee como propiedad: cuenta.saldo
  }
  set saldo(valor) {
    throw new Error("Usa depositar()"); // cuenta.saldo = 5 llega aquí
  }
  depositar(monto) {
    this.#saldo += monto * (1 - Cuenta.comision);
  }
}
```

- **`#campo`** es privado de verdad: lo garantiza el lenguaje, no una convención como `_campo`.
  En la oficina es un cajón con llave en el escritorio de cada empleado, y la llave solo la tiene
  el código escrito dentro de la clase. Usarlo fuera es un `SyntaxError`, y no aparece en
  `Object.keys` ni en `JSON.stringify`.
- **`static`** pone el miembro en el propio departamento, la clase. Lo usas para fábricas
  (`HttpError.fromStatus(…)`) o, en React, para `getDerivedStateFromError`, que React busca
  en la clase, no en la instancia.
- **`get`/`set`** definen propiedades calculadas en el jefe común: se leen y asignan sin
  paréntesis, pero ejecutan código. Es el setter heredado que viste antes, con mejor sintaxis.

## extends: alargar la cadena

Cuarta capa. `extends` le pone jefe al jefe: el jefe común de los perros pasa a tener como jefe
al de los animales. Y enlaza **dos** cadenas, no una: también el departamento `Dog` tiene como
jefe al departamento `Animal`, por eso los `static` se heredan.

```js
class Animal {
  constructor(name) {
    this.name = name;
  }
  describe() {
    return this.name + " hace " + this.sound();
  }
  sound() {
    return "...";
  }
}

class Dog extends Animal {
  constructor(name, raza) {
    super(name); // ejecuta el constructor de Animal
    this.raza = raza;
  }
  sound() {
    return "guau"; // shadowing: tapa Animal.prototype.sound
  }
  describe() {
    return super.describe() + " (" + this.raza + ")"; // llama a la versión del padre
  }
}
```

```text
new Dog(…) ──▶ Dog.prototype ──▶ Animal.prototype ──▶ Object.prototype ──▶ null
  name, raza    sound, describe   describe, sound
```

Dos reglas de `super`:

- En el constructor de una clase derivada tienes que llamar a `super(…)` **antes** de usar
  `this`. Hasta ese momento la instancia no existe (usar `this` antes lanza `ReferenceError`).
- `super.metodo()` busca `metodo` empezando en el prototipo del padre, y lo ejecuta con el
  `this` actual. Es saltarte a tu jefe y preguntarle directamente al de arriba.

<Profundiza titulo="por qué la instancia no existe antes de super">

En una clase base, `new` crea el objeto antes de ejecutar el constructor. En una derivada no:
el objeto lo crea el constructor del padre, y `super(…)` es la llamada que lo hace. Por eso
`this` no está disponible antes, y por eso extender clases del lenguaje da instancias de verdad:

```js
class Lista extends Array {}
const l = new Lista();
l[4] = "x";
console.log(l.length, Array.isArray(l)); // 5 true
```

Lo mismo con `extends Error`: el objeto lo construye `Error`. Y si una clase derivada no declara
`constructor`, tiene uno implícito que llama a `super(...args)`.

</Profundiza>

<AntesDeSeguir>

Un método `static` usa `this`. ¿Qué imprime?

```js
class Animal {
  static crear(name) {
    return new this(name);
  }
  constructor(name) {
    this.name = name;
  }
}
class Dog extends Animal {}
const toby = Dog.crear("Toby");
console.log(toby instanceof Dog, toby.name);
console.log(Object.getPrototypeOf(Dog) === Animal, typeof toby.crear);
```

<Respuesta>

```
true Toby
true undefined
```

`Dog` no tiene `crear` y pregunta a su jefe, `Animal`. Como lo llamaste con `Dog.crear`, `this`
es `Dog`, y `new this(…)` fabrica un perro. `toby` no ve `crear`: su cadena pasa por los
`.prototype`, nunca por las clases.

</Respuesta>

</AntesDeSeguir>

### Qué pregunta instanceof

**`instanceof`** no mira "de qué clase es" el objeto ni quién lo construyó: comprueba si
`Clase.prototype` aparece en algún punto de su cadena de jefes. `new Dog("Rex") instanceof Animal`
es `true` porque `Animal.prototype` está dos pisos arriba.

<AntesDeSeguir>

¿Qué imprime?

```js
class Dog {
  constructor(name) {
    this.name = name;
  }
}
const impostor = Object.create(Dog.prototype);
console.log(impostor instanceof Dog, impostor.name);
const rex = new Dog("Rex");
Object.setPrototypeOf(rex, null);
console.log(rex instanceof Dog, rex.name);
```

<Respuesta>

```
true undefined
false Rex
```

El constructor de `Dog` nunca se ejecutó para `impostor`, pero su jefe es `Dog.prototype`, y eso
es todo lo que mira `instanceof`. A `rex` le quitaste el jefe: conserva su libreta, pero ya no
está en la cadena. `instanceof` pregunta por la cadena, no por la historia del objeto.

</Respuesta>

</AntesDeSeguir>

## Errores propios

`Error` es una clase más, y extenderla te da errores que puedes distinguir con `instanceof` en un
`catch` (o en tu error boundary):

```js
class HttpError extends Error {
  constructor(status, message, options) {
    super(message, options); // options.cause conserva el error original
    this.name = "HttpError";
    this.status = status;
  }
}

try {
  const res = await fetch(url);
  if (!res.ok) throw new HttpError(res.status, "Fallo al cargar " + url);
} catch (error) {
  if (error instanceof HttpError && error.status === 401) redirigirALogin();
  else throw error;
}
```

Esta pregunta encadena dos niveles de errores: qué se hereda y qué no.

<Pregunta id="clases-error-propio" />

<Callout type="clave">
Una clase es una función constructora más un objeto `.prototype` con sus métodos. Las instancias guardan sus datos (propiedades propias, campos, `#privados`) y encuentran los métodos subiendo por la cadena de prototipos. `extends` alarga esa cadena, `super` sube un eslabón e `instanceof` la recorre.
</Callout>

## El ticket, resuelto

**¿Por qué `error.name` dice `"Error"`?** `NotFoundError` nunca anota `name` en la libreta del
error, así que la lectura sube: `NotFoundError.prototype` no lo tiene, `Error.prototype` sí, y
vale `"Error"`: la comparación del boundary nunca podía ser cierta. Asigna `this.name` tú mismo,
con un literal (deducirlo de `this.constructor.name` es frágil: los minificadores pueden
renombrar las clases).

**¿Es fiable `instanceof`?** Sí: comprueba si `NotFoundError.prototype` está en la cadena del
error, y lo está porque se creó con `new NotFoundError(…)`. El boundary queda así:

```jsx
if (error instanceof NotFoundError) return <UsuarioNoExiste />;
```

**¿De dónde salen `this.props` y `setState`?** `ErrorBoundary` no declara constructor, así que
el implícito llama a `super(...args)`, y el constructor de `Component` anota `props` en la
libreta de la instancia. `setState` vive una sola vez en `Component.prototype`, el jefe del jefe
de cada instancia. (React también marca `Component.prototype` con `isReactComponent` y busca esa
marca para saber si un componente necesita `new`: `typeof` no le serviría, una clase también es
una función.)

**¿Por qué `static`?** React busca `getDerivedStateFromError` en la clase
(`ErrorBoundary.getDerivedStateFromError`), no en la instancia, así que tiene que vivir en el
departamento. (Si lo declaras sin `static`, React lo ignora y, en desarrollo, te avisa en consola.) `state = …` es un campo: se anota en cada instancia. `render` es un método:
vive una sola vez en `ErrorBoundary.prototype`.

## Lo que ahora puedes explicar

Ya sabes qué es una clase en JavaScript: una función, un objeto `.prototype` con los métodos y
una cadena de jefes que se recorre al leer. Sabes por qué leer sube y escribir no, por qué un
array en un prototipo es una pizarra compartida y dónde acaba cada miembro de una clase. Y sabes
que `instanceof` es fiable porque pregunta por la cadena, que es lo único que de verdad existe.

Has visto de pasada que un objeto literal también tiene jefe: `"toString" in {}` es `true`. Eso
importa cuando usas un objeto como diccionario, y es uno de los puntos de partida de la
siguiente lección, **Objetos y colecciones**: cómo recorrer y describir propiedades, qué
significa de verdad "enumerable" y cuándo un `Map` es mejor diccionario que un objeto.
