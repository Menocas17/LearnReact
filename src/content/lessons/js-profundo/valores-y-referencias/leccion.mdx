## Tres bugs en la misma pantalla

> **#457 — "El tablero no se entera de nada".** Al añadir una tarea no aparece; aparece de golpe
> cuando escribes en el buscador. Mientras escribes, el indicador del chat parpadea
> "reconectando" con cada letra. Y si editas el responsable de una tarea y pulsas Cancelar, el
> cambio se queda.

Abres el código. Así se añade una tarea:

```jsx
const [todos, setTodos] = useState([]);

function handleAdd(text) {
  todos.push({ id: crypto.randomUUID(), text });
  setTodos(todos); // la tarea está en el array… pero no se repinta nada
}
```

Así se conecta el chat:

```jsx
function ChatRoom({ roomId }) {
  const [message, setMessage] = useState("");
  const options = { serverUrl: "https://localhost:1234", roomId };

  useEffect(() => {
    const connection = createConnection(options);
    connection.connect();
    return () => connection.disconnect();
  }, [options]);
  // <input value={message} onChange={(e) => setMessage(e.target.value)} />
}
```

Y así se edita una tarea, con un borrador:

```jsx
function handleEdit(task) {
  setDraft({ ...task });
}

function handleAssigneeChange(e) {
  draft.assignee.name = e.target.value; // es el borrador, se puede tocar
  setDraft({ ...draft });
}

function handleCancel() {
  setDraft(null); // descarta el borrador… o eso debería
}
```

Tres síntomas sin relación aparente:

1. ¿Por qué React no ve una tarea que **sí** está en el array?
2. ¿Por qué el efecto ve un cambio en `options` que **no** ocurrió?
3. ¿Por qué Cancelar no deshace nada, si el borrador era una copia?

Las tres tienen una sola respuesta: cómo guarda, copia y compara JavaScript los objetos. React
no inventó nada aquí; solo se apoya en esas reglas.

## Por qué JavaScript no copia tus objetos

JavaScript tiene dos familias de valores:

- **Primitivos**: `string`, `number`, `bigint`, `boolean`, `undefined`, `null` y `symbol`. Son
  **inmutables**: no hay forma de cambiar el número `3` o el string `"hola"`; solo puedes crear
  otro valor. Incluso `texto.toUpperCase()` devuelve un string nuevo.
- **Objetos**: todo lo demás, incluidos arrays, funciones, `Date`, `Map`… Son **mutables**:
  puedes cambiar su contenido.

Esa división no es un capricho. Un primitivo es pequeño y no cambia: copiarlo es barato y seguro.
Un objeto puede tener cualquier tamaño (un array con cien mil filas, un nodo del DOM con todo su
subárbol): si cada asignación duplicara el objeto entero, pasar tu estado a un helper costaría
tanto como el estado mismo. Y a menudo quieres justo que dos partes del programa trabajen sobre
**el mismo** objeto.

Por eso JavaScript, igual que Java o Python, no copia los objetos: copia un **acceso** a ellos.
Esa decisión tiene un precio, y ese precio son los tres bugs del ticket.

## El almacén y las fichas

Imagina un **almacén** con estantes numerados, y tu escritorio lleno de **fichas**. Esta imagen te
va a acompañar toda la lección.

**Cada variable es una ficha.** Si guarda un primitivo, el valor va escrito en la ficha misma:
`3`, `"Ana"`, `true`. Si guarda un objeto, el objeto no cabe en la ficha: es una **caja** que vive
en un estante del almacén, y la ficha solo dice **"caja del estante 17"**. Ese número es la
**referencia**.

Y la regla de oro: **asignar una variable a otra siempre fotocopia la ficha**. Con un primitivo,
la fotocopia lleva el valor. Con un objeto, lleva el número de estante: ahora hay dos fichas que
llevan a **la misma** caja.

<AntesDeSeguir>

¿Qué imprime esto?

```js
let a = 1;
let b = a;
b = 2;

const x = { n: 1 };
const y = x;
y.n = 2;

console.log(a, x.n);
```

<Respuesta>

```
1 2
```

`b` recibió una fotocopia del `1` y luego se reescribió; `a` no se entera. `y` recibió una
fotocopia de "estante 17", y `y.n = 2` cambió **la caja**, que es la misma de `x`.

</Respuesta>

</AntesDeSeguir>

### Reescribir la ficha o tocar la caja

Ahí se esconden las dos operaciones que más se confunden:

- **Asignar** (`y = otraCosa`) **reescribe tu ficha**: cambia a qué apunta una variable. No afecta
  a nadie más.
- **Mutar** (`y.n = 2`, `arr.push(4)`, `delete obj.k`) **abre la caja** y cambia su contenido. Lo
  ve cualquiera que tenga una ficha de ese estante.

<AntesDeSeguir>

¿Qué imprime? Fíjate en que `user` es `const`.

```js
const user = { name: "Ana" };
const alias = user;
alias.name = "Luis";

let otro = user;
otro = { name: "Eva" };

console.log(user.name, otro.name);

try {
  user = { name: "Sara" };
} catch (e) {
  console.log(e.name);
}
```

<Respuesta>

```
Luis Eva
TypeError
```

`alias.name = "Luis"` mutó la caja que comparten `user` y `alias`. `otro = { name: "Eva" }` solo
reescribió la ficha de `otro`. Y la última línea lanza `TypeError` porque `user` es `const`.

Pero `const` **no** impidió la mutación: **plastifica la ficha** (no puedes reasignar la
variable), pero no cierra la caja. `const` no hace inmutable un objeto.

</Respuesta>

</AntesDeSeguir>

### Pasar una ficha a una función

Pasar un argumento a una función es exactamente una asignación: el parámetro recibe una
fotocopia de la ficha. Con un primitivo, la función no puede alterar la variable de fuera. Con un
objeto, recibe el número de estante: puede **mutar** la caja compartida, pero si **reasigna** el
parámetro solo reescribe su propia fotocopia. Técnicamente JavaScript siempre pasa "por valor";
con objetos, ese valor es una referencia. Nunca puede hacer que la variable del que llama apunte
a otra cosa.

<Profundiza titulo="¿por valor o por referencia?">

Ningún nombre encaja del todo. En el paso por referencia de verdad (`ref` en C#, `&` en C++), la
función recibe la variable misma y puede hacer que la de fuera apunte a otro sitio; en JavaScript
eso es imposible. Por eso hay quien usa un tercer nombre, *call by sharing* ("paso por
compartición"), acuñado por el equipo de Barbara Liskov para el lenguaje CLU en los años 70: se
pasa una copia de la referencia y el objeto queda compartido.

</Profundiza>

Esta pregunta pone a prueba justo esa frontera entre mutar la caja y reescribir la fotocopia:

<Pregunta id="referencias-parametro-reasignado" />

## Comparar fichas, no cajas

`===` compara primitivos por valor, pero objetos por **identidad**: solo mira si las dos fichas
dicen el mismo número de estante. **Nunca abre las cajas.** Dos objetos creados por separado son
dos cajas en dos estantes, aunque tengan dentro exactamente lo mismo:

```js
console.log({} === {});         // false: dos objetos distintos
console.log([1, 2] === [1, 2]); // false
const a = [1, 2];
console.log(a === a);           // true
```

¿Por qué no abre las cajas? Porque comparar contenidos no es barato ni está bien definido: habría
que bajar a cada objeto anidado y decidir qué hacer con ciclos, funciones o prototipos. Comparar
dos números de estante es instantáneo y sin ambigüedad. No existe en el lenguaje una comparación
de contenido incorporada; si la necesitas, la escribes tú (o comparas campos concretos).

Esta pregunta comprueba que distingues identidad de contenido:

<Pregunta id="referencias-igualdad-objetos" />

React no usa `===`, sino `Object.is`, que es igual salvo en dos casos de números:
`Object.is(NaN, NaN)` es `true` (con `===`, `NaN` no es igual ni a sí mismo) y `Object.is(0, -0)`
es `false`. Con objetos se comporta igual: compara fichas, no cajas.

<Profundiza titulo="Record & Tuple: el intento de comparar cajas">

El comité que evoluciona JavaScript (TC39) estudió una propuesta de *records* y *tuples*:
estructuras inmutables, escritas `#{ id: 1 }` y `#[1, 2]`, que se compararían por contenido
(`#[1, 2] === #[1, 2]` sería `true`). Llegó a la etapa 2, pero se retiró.

</Profundiza>

## React solo mira la ficha

React guarda las fichas del render anterior y, cuando necesita saber si algo cambió, las compara
con `Object.is`. No abre las cajas. Lo hace en tres sitios clave:

1. **Al actualizar el estado.** Si `Object.is(anterior, nuevo)` es `true`, React asume que nada
   cambió y puede omitir el render.
2. **En los arrays de dependencias** de `useEffect`, `useMemo` y `useCallback`: compara cada
   dependencia con la del render anterior.
3. **En `memo`**: por defecto, un componente envuelto en `memo` compara cada prop con la anterior
   usando `Object.is`, y si todas coinciden se salta el render.

¿Por qué no compara contenidos? Abrir cada caja anidada en cada render costaría tiempo
proporcional al tamaño del estado. La documentación de React lo da como razón para tratar el
estado como inmutable: si nunca modificas una caja y creas una nueva cuando algo cambia, comparar
fichas basta para saber qué cambió. (La otra razón: conservar intactas las versiones anteriores
facilita cosas como deshacer.)

<AntesDeSeguir>

Este es un `setState` de juguete que hace la misma comprobación que React. ¿Qué imprime?

```js
let estado = [];
let renders = 0;

function setEstado(nuevo) {
  if (Object.is(estado, nuevo)) return; // "no cambió": no renderiza
  estado = nuevo;
  renders++;
}

const todos = estado;
todos.push("pan");
setEstado(todos);
console.log(renders, estado.join(","));

setEstado([...estado, "leche"]);
console.log(renders, estado.join(","));
```

<Respuesta>

```
0 pan
1 pan,leche
```

`push` metió `"pan"` en la caja, pero `setEstado` recibió **la misma ficha**: no hay cambio ni
render. El dato está ahí, invisible, hasta que llega una ficha nueva y el render muestra la caja
tal como está, con el `"pan"` que se coló antes.

</Respuesta>

</AntesDeSeguir>

Y eso es, palabra por palabra, el primer síntoma del ticket: "aparece de golpe cuando escribes en
el buscador". Esta pregunta pone a prueba que sabes explicarlo en React:

<Pregunta id="referencias-react-push" />

La solución es entregar una ficha nueva, de una caja nueva:

```jsx
setTodos([...todos, { id: crypto.randomUUID(), text }]); // array nuevo
```

<AntesDeSeguir>

Ahora el chat. En cada render, `ChatRoom` ejecuta su cuerpo de nuevo, incluida la línea
`const options = { serverUrl, roomId }`. Si el usuario escribe una letra y `roomId` sigue siendo
`"general"`, ¿qué ve React al comparar la dependencia `options` con la del render anterior? ¿Y si
la dependencia fuera `roomId`?

<Respuesta>

Un objeto literal crea **una caja nueva cada vez que se ejecuta**, aunque el contenido sea
idéntico. `Object.is(optionsAnterior, optionsNuevo)` es `false`: para React la dependencia cambió,
así que limpia el efecto (desconecta) y lo vuelve a ejecutar (conecta), con cada letra.

`roomId`, en cambio, es un primitivo escrito en la ficha: `Object.is("general", "general")` es
`true`, y el efecto no se repite.

</Respuesta>

</AntesDeSeguir>

La solución es depender de primitivos y crear el objeto dentro del efecto:

```jsx
useEffect(() => {
  const options = { serverUrl: "https://localhost:1234", roomId };
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, [roomId]); // un string: se compara por valor
```

Lo mismo vale para una función definida en el cuerpo del componente: es una caja nueva en cada
render, y como dependencia o como prop de un componente con `memo` anula la comparación.

<Callout type="clave">
En React, "cambió" significa "es otra referencia". Por eso el estado se trata como inmutable: para cambiar algo creas un objeto o array nuevo, y para que algo no cuente como cambio, mantienes la misma referencia.
</Callout>

## Cajas dentro de cajas

Queda Cancelar. El borrador se creó con `{ ...task }`, que sí crea una caja nueva. ¿Entonces?

<AntesDeSeguir>

¿Qué imprime?

```js
const task = { title: "Comprar pan", assignee: { name: "Ana" } };
const draft = { ...task };

draft.title = "Comprar leche";
draft.assignee.name = "Luis";

console.log(task.title, task.assignee.name);
console.log(draft === task, draft.assignee === task.assignee);
```

<Respuesta>

```
Comprar pan Luis
false true
```

El spread creó una caja nueva y **fotocopió las fichas que había dentro**. `title` era un
primitivo: la copia lleva su propio texto. Pero la ficha de `assignee` decía "estante 42", y la
fotocopia dice lo mismo: las cajas exteriores son dos, la del responsable es **una sola**.

</Respuesta>

</AntesDeSeguir>

Eso es una **copia superficial**: un contenedor nuevo con las propiedades copiadas tal cual. Si
una propiedad es un objeto, se copia su referencia y el objeto anidado queda compartido. La hacen
el spread (`...`), `Object.assign`, `Array.from` o `slice()`. Una **copia profunda**, en cambio,
duplica también todos los objetos anidados, de modo que la copia no comparte nada con el
original.

Esta pregunta pone a prueba la diferencia entre mutar una caja anidada compartida y reasignar
una propiedad de la copia:

<Pregunta id="inmutabilidad-spread-anidado" />

### structuredClone y sus límites

`structuredClone(valor)` hace una copia profunda usando el algoritmo de clonado estructurado (el
mismo que usa `postMessage` para enviar datos a un worker o a otra ventana). Está disponible en
navegadores modernos y en Node 17+.

```js
const original = { when: new Date(0), tags: new Map([["a", 1]]), list: [{ n: 1 }] };
const clone = structuredClone(original);

clone.list[0].n = 2;
original.list[0].n;          // 1: no comparten nada
clone.when instanceof Date;  // true: copia Date, Map, Set, arrays, objetos planos…
```

Pero está pensado para **datos** que viajan, no para todo.

<AntesDeSeguir>

¿Qué imprime?

```js
class Tarea {
  constructor(title) { this.title = title; }
  resumen() { return this.title; }
}

const clon = structuredClone(new Tarea("Pan"));
console.log(clon.title, clon instanceof Tarea, typeof clon.resumen);

try {
  structuredClone({ title: "Pan", onSave() {} });
} catch (e) {
  console.log(e.name);
}
```

<Respuesta>

```
Pan false undefined
DataCloneError
```

La instancia vuelve como objeto plano: los datos sí, la clase y sus métodos no. Y un objeto con
una función ni siquiera se puede clonar.

</Respuesta>

</AntesDeSeguir>

Sus límites, completos:

- **No clona funciones** (ni objetos que las contengan como valor) ni nodos del DOM: lanza un
  `DOMException` llamado `DataCloneError`.
- **No conserva prototipos**: una instancia de una clase propia vuelve como objeto plano, sin sus
  métodos. Los getters se ejecutan y se copia su valor como propiedad normal (el getter/setter en
  sí se pierde), y se omiten las propiedades con clave de símbolo y las no enumerables.
- Sí respeta referencias circulares y objetos repetidos.

`JSON.parse(JSON.stringify(x))` es el truco antiguo y es peor: convierte `Date` en strings, pierde
`undefined`, `Map` y `Set`, y falla con referencias circulares.

¿Entonces el borrador se arregla con `structuredClone`? Funcionaría, pero con estado de React
casi nunca necesitas una copia profunda: copiar todo es caro y **rompe las referencias de lo que
no cambió**: cada caja clonada es una ficha nueva, y `memo` o un efecto creerán que todo cambió.
Lo que necesitas es copiar **solo el camino** hasta lo que cambia.

### Precintar una caja: Object.freeze es superficial

¿Y si precintas las cajas? `Object.freeze(obj)` (existe desde ES5) impide añadir, quitar o reasignar propiedades **de ese
objeto**. En modo estricto (los módulos ES y las clases lo son) intentarlo lanza `TypeError`;
fuera de él falla en silencio.

Pero el precinto es solo de **esa** caja: las cajas a las que llevan sus fichas siguen abiertas.
Esta pregunta comprueba que lo ves:

<Pregunta id="inmutabilidad-freeze-superficial" />

Para congelar en profundidad hay que recorrer el objeto y llamar a `Object.freeze` en cada nivel.
Es útil en tests o en desarrollo para detectar mutaciones accidentales.

## Los métodos que abren la caja

El origen más común de mutaciones accidentales es un método de array que trabaja **dentro de la
caja** sin que lo parezca:

| Mutan el array | Devuelven un array nuevo |
|---|---|
| `push`, `pop`, `shift`, `unshift` | `concat`, `[...arr, x]`, `slice` |
| `splice` | `toSpliced` (ES2023), `filter` |
| `sort` | `toSorted` (ES2023) |
| `reverse` | `toReversed` (ES2023) |
| `arr[i] = x`, `fill`, `copyWithin` | `with(i, x)` (ES2023), `map` |

Antes de ES2023, ordenar sin mutar exigía `[...arr].sort()`; `toSorted`, `toReversed`,
`toSpliced` y `with` llenaron ese hueco.

<AntesDeSeguir>

¿Qué imprime?

```js
const prioridades = [10, 9, 1];
const ordenadas = prioridades.sort();

console.log(ordenadas.join(","), prioridades.join(","));
console.log(ordenadas === prioridades);
```

<Respuesta>

```
1,10,9 1,10,9
true
```

Dos sorpresas. `sort` y `reverse` **mutan y además devuelven** el mismo array: la línea parece
inofensiva, pero las dos fichas llevan a la misma caja, ya ordenada. Y sin comparador, `sort`
ordena como strings: `"10"` va antes que `"9"`. Para números, `(a, b) => a - b`.

</Respuesta>

</AntesDeSeguir>

## Copiar solo el camino

La regla de actualización inmutable: **copia cada caja en el camino desde la raíz hasta lo que
cambia; reutiliza todas las demás fichas**. Lo que no cambia conserva su referencia (*structural
sharing*), lo que hace la copia barata y permite que `memo`, `useMemo` o las dependencias de un
efecto sepan que esas partes no cambiaron.

```js
// Objeto anidado: cambiar state.user.address.city
const next = {
  ...state,
  user: {
    ...state.user,
    address: { ...state.user.address, city: "Quito" },
  },
};
// next.user !== state.user (estaba en el camino)
// next.settings === state.settings → true (no estaba en el camino)
```

Tres cajas nuevas y todo lo demás compartido: un componente con `memo` que recibe `settings` ni
se entera.

Con arrays:

```js
[...todos, nueva];                                   // añadir al final
[nueva, ...todos];                                   // añadir al principio
todos.filter((t) => t.id !== id);                    // eliminar
todos.map((t) => (t.id === id ? { ...t, done: !t.done } : t)); // actualizar uno
todos.toSpliced(index, 0, nueva);                    // insertar en una posición
todos.with(index, reemplazo);                        // reemplazar por índice
todos.toSorted((a, b) => a.text.localeCompare(b.text)); // ordenar
```

Fíjate en el `map`: copia solo la tarea que cambia (`{ ...t, done: !t.done }`) y devuelve las
demás tal cual. Es la versión en array de copiar el camino.

<AntesDeSeguir>

Alguien intenta atajar: "copio el array y ya puedo tocarlo". ¿Qué imprime?

```js
const todos = [
  { id: 1, done: false },
  { id: 2, done: false },
];

const copia = [...todos];
copia[0].done = true;

console.log(todos[0].done, copia === todos, copia[0] === todos[0]);
```

<Respuesta>

```
true false true
```

La caja del array es nueva, pero dentro están las mismas fichas: la tarea es el mismo objeto en
ambos arrays, y `copia[0].done = true` muta el estado original. La tarea está en el camino: hay
que copiarla también, como hace el `map`.

</Respuesta>

</AntesDeSeguir>

Con anidamiento profundo, librerías como Immer te dejan escribir código "mutante" sobre un
borrador y generan la copia inmutable por ti; por debajo hacen exactamente esto.

<Callout type="cuidado">
Errores comunes:

- Creer que `const` hace inmutable un objeto: solo impide reasignar la variable.
- Copiar con spread y luego mutar un objeto anidado: la copia superficial comparte los niveles inferiores.
- Usar `sort`, `reverse` o `splice` sobre el estado (o sobre props): mutan el original. Usa `toSorted`, `toReversed` y `toSpliced`.
- Comparar objetos o arrays con `===` esperando comparar su contenido.
- Poner en las dependencias de un efecto un objeto o función creado durante el render: es nuevo en cada render.
- Abusar de `structuredClone` para actualizar estado: copia todo, rompe el structural sharing y no admite funciones.
</Callout>

## El ticket, resuelto

Vuelve al #457 con el almacén en la cabeza.

**¿Por qué React no ve la tarea?** `push` metió la tarea en la caja del estado y `setTodos(todos)`
entregó la misma ficha: `Object.is` da `true` y React omite el render. La tarea aparece con el
siguiente cambio de verdad, que muestra la caja tal como quedó. Arreglo:
`setTodos([...todos, nueva])`.

**¿Por qué el efecto ve un cambio que no ocurrió?** Cada render crea una caja `options` nueva con
el mismo contenido: fichas distintas, dependencia "cambiada", reconexión con cada letra. Arreglo:
crear `options` dentro del efecto y depender de `roomId`, un primitivo.

**¿Por qué Cancelar no deshace?** `{ ...task }` es una copia superficial: la ficha de `assignee`
lleva al mismo objeto que usa la tarea de la lista, y `draft.assignee.name = ...` lo modificó.
`setDraft(null)` tira el borrador, pero el daño ya estaba en la caja compartida. Arreglo: copiar
el camino, `setDraft({ ...draft, assignee: { ...draft.assignee, name: e.target.value } })`.

Tres síntomas, una causa: **fichas que se comparan sin abrir las cajas, y cajas que se comparten
sin que lo parezca**.

## Lo que ahora puedes explicar

Si alguien en tu equipo dice "React no detecta mis cambios", ya sabes qué preguntar: ¿le diste
una ficha nueva o solo tocaste la caja? Sabes que asignar y pasar argumentos fotocopia la
referencia, que `===` y `Object.is` comparan estantes y nunca contenidos, por qué el spread no
